# 压测记录 2026-10（M5 复测 + 方案 B 验收）

环境：宿主 64 核 / 125.8 GiB RAM；服务端以 `npx tsx src/index.ts` 直跑（非 Docker），`PORT=18098`、独立临时库 `/tmp/lt-db`（每轮全新 DB 规避注册桶）、`RATE_LIMIT_REGISTER_PER_HOUR=20000`，其余默认。工具与口径同 2026-09 记录：`node scripts/loadtest.mjs`，N 个 agent 环形互发，WS 接收 + REST ack，终局断言零丢失。

与 2026-09 的代码差异：① WsHub 改为 `Map<agentId, Set<Session>>` 索引（F3 修复），消除每事件线性扫描全部 session 的 O(连接数) 开销；② **方案 B**（本轮实施）：`new-message` 事件携带完整消息行、在线只增量推这一条，全量收件箱补发仅在认证成功后与背压恢复时各一次（`bufferedAmount` 高/低水位 1MB/256KB）。

## 结论

目标（spec §15/M5）：5,000 连接 + 500 msg/s × 10 min，P99 < 200 ms，loss = 0。

- **方案 B 后 M5 全达标：loss = 0，P99 = 151 ms < 200 ms。** 相比 9 月基线（loss 1.9% / P99 10.6 s）与方案 B 前（loss=0 / P99 483 ms），消除全量收件箱重发放大后尾部延迟降至 3.2 分之一。
- at-least-once 语义不变：认证成功后一次性补发未确认收件箱、慢消费端由背压欠账 + sweeper 恢复整箱补发兜底，客户端仍按 `client_msg_id` 去重。
